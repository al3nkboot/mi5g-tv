## Verdict: MERGE

No blocker or high finding. The module does what its row asks: the export round trip holds, the
generated `restore.sh` restores the baseline under every POSIX shell in the build container, the
generated `restore.ps1` now has run too (below) and reaches the same end state as `restore.sh` in
every scenario tried, the note fits the page, and no file carries the serial, the address, the
subnet or Wi-Fi data. Six small defects were fixed in R5 commits. M1 and M2 below are follow-ups
for W6 before integration gate I2, not reasons to hold the merge: on every flow 0.1 records in one
plan they restore correctly, and they do not change a frozen interface.

## Findings

Severity: High (wrong result or unsafe), Medium (wrong in a reachable flow, or a claim that does
not hold), Low (robustness, consistency), Info.

### M1 (Medium, open) The laptop scripts replay every inverse; the phone undoes the net effect

`RestoreCommands.kt:29-38`. The scripts carry the inverse of every recorded change, newest first.
The planner's `UndoEverything` (W3, `DefaultPlanner.undoEverything`) instead takes the earliest
record per target (the original state), then packages, settings, the stock home, uninstalls, in
that order, skipping targets already right. Both reach the baseline when every intermediate step
succeeds, so the scenario test passes, but:

- the DECISIONS claim D-W6-1 ("the same lines the phone would run for the same undo") holds per op,
  not per undo: the two undos are different command lists;
- a reachable flow goes through a bad intermediate state. Setup (install launcher, SetHome launcher,
  disable stock), later the app's "TV's own home screen" plus "remove the new one" (Enable stock
  prior DISABLED_USER, SetHome stock prior launcher, Uninstall launcher prior present=true). The
  generated script then: skips the uninstall with "the app cannot be reinstalled from here"
  (misleading, it is our own launcher the user removed on purpose); runs `set-home-activity` to the
  removed launcher (FAILED); runs `pm disable-user` on the stock launcher, which succeeds and leaves
  the TV with no enabled home screen until two steps later; then puts the stock home back; with
  `--remove-apps` the final uninstall FAILS too. End state right, exit 1, and an interrupted run
  (Ctrl-C, a dropped Wi-Fi link) at that point leaves a TV without a home screen.

Recommendation: derive the laptop steps from the net effect (earliest prior per package, per
setting, the first SetHome's prior, our installs not removed since), ordered packages, settings,
home, uninstalls, files, the same shape as W3, ideally one shared helper so the two cannot drift.
Not fixed in R5: it is a design change with test rework, not a small fix.

### M2 (Medium, open) Undo semantics are tested against a stand-in renderer whose inverse differs from W3's

`src/test/.../ReferenceRenderer.kt:54-71` versus W3 `ShellRenderer.inverse` (sibling branch). W3
returns `null` for "already in that state" cases (Disable with prior DISABLED or DISABLED_USER,
Enable with prior ENABLED, DefaultState with prior DEFAULT, SettingsPut of `adb_enabled` or
`adb_wifi_enabled`); the stand-in returns an op. With the real renderer those records become
`NOT_FROM_LAPTOP` "this change has no undo" entries (`RestoreCommands.kt:38`, `:112`), which tells
the user something could not be put back when nothing needed to be. W3 also quotes the verb words
(`'pm' 'enable' ...`); the stub adb accepts that, so the shell tests should pass with it.
Recommendation: when `:core:ops` lands, run `RestoreShellTest` with `ShellRenderer` (as W6 itself
notes) and treat a `null` inverse of a no-op change as no step.

### L1 (Low, fixed) Zip bytes depended on the JVM default time zone

`RestoreBundle.kt:135`. `ZipEntry.time` converts to DOS local time with the default zone, so the
"same inputs, same bytes" claim (D-W6-8) held only on one device setting. Now `timeLocal` in the
writer's own `zone`. Test `theBytesDoNotDependOnTheDefaultTimeZone`.

### L2 (Low, fixed) A manifest listing an entry twice was accepted

`RestoreBundle.kt:176-184`. `associate` kept the last of duplicate names silently. Now refused.
Test `aManifestThatListsAnEntryTwiceIsRefused`.

### L3 (Low, fixed) restore.ps1 on Windows PowerShell 5.1 would report a false FAILED on any stderr

`RestoreScripts.kt:289-291`, `:339`. In 5.1, `2>&1` wraps each native stderr line in an error
record whose text includes `NativeCommandError` and `RemoteException`; `Out-String` then contains
"Exception" and `Step` marks a successful line FAILED. Each record is now turned into its plain text
first. The failure match is also case-sensitive now (`-cnotmatch`), like the `case` in restore.sh.
Verified on PowerShell 7.4 (below); 5.1 itself is still unexecuted (no Windows host).

### L4 (Low, fixed) The longest restore note was exactly 60 lines

`PlainRestoreNote.kt:52-60`. With more than 40 names, HOME replaced and a module installed, the note
was 60 lines; the row asks for under 60. The closing "The same list is on the TV" line repeated what
the "and N more, listed on the TV" line says; it is now left out when the list collapses (59 lines).
Test `theLongestNoteStaysUnderSixtyLines`.

### L5 (Low, fixed) Same-millisecond records ordered by list position, not by plan step

`RestoreCommands.kt:64-70`, `ChangeSummary.kt:38`, `RestoreBundle.kt:97`. Now `(atMs, step)` then
list order, the order W3's undo reads records in. Test `sameMillisecondFallsBackToThePlanStep`.

### L6 (Low, fixed) Invisible U+2028 and U+2029 literals in source

`TextSafety.kt:25`. Written as `' '` and `' '` escapes; behaviour unchanged.

### L7 (Low, open) The nickname is written to the TV's shared storage

`DefaultTvRestoreFiles.kt:73`. D-W6-6 keeps the nickname out of `restore-point.json` because any app
can read `/sdcard` on Android 9 and 10, but `restore.txt` in the same folder names the TV by nickname
("Mi TV 4A (Living room)" style text a family may type). Not serial, address or Wi-Fi data, so the
row's rule holds; recommend the model only, consistent with D-W6-6.

### L8 (Low, open) TV-provided text reaches the laptop terminal unfiltered

`RestoreScripts.kt:206/214` and `:320` (the model in the wrong-TV message), `:241-242` and `:346`
(what the TV printed for a FAILED step). A TV that answers at the address (D37 says identity is not
cryptographic on plain 5555) can put terminal escape sequences on the user's screen. Never executed
as code (checked below). Recommend stripping to printable ASCII (`tr -cd ' -~\n'`, `-replace
'[^\x20-\x7E\r\n]'`) before printing.

### L9 (Info) Phone-local blob paths are written into changes.json and restore-point.json

`ChangeJson.kt:194` writes `BlobRef.path` (a path in the app's private storage or a bundled asset
name) into both files, and `restore-point.json` lands on the TV's shared storage. No personal data,
but nothing reads it back; consider omitting `path` from the export.

### L10 (Info) Smaller notes

- `RestoreBundleReader` reads local headers (`ZipInputStream`, `RestoreBundle.kt:159`) and ignores
  the central directory, so a crafted zip can show a desktop unzip different files than the app
  reads. The manifest hash checks still bind what the app reads; matters only for the 0.2 import.
- `DocumentSnapshotStore.load`, `baseline` and `latest` throw on a corrupt or mismatched document
  (`DocumentSnapshotStore.kt:66`) instead of returning null. Defensible (a null baseline could
  invite a new one and lose the original); W8 should catch it and say so.
- `restore.txt` through upstream `tools/restore.sh` enables every listed package, so a package that
  was in the DEFAULT state comes back ENABLED. A limit of the upstream format, stated for the record.
- The privacy test (`RestoreBundleTest.noSerialOrNetworkDataInAnyFile`) covers every zip entry and
  both TV files but not the restore note; the note's inputs (nickname, room, model, friendly names,
  date) carry no serial or network data, so this is a coverage gap, not a leak.

## Checked and fine

- Undo ordering: newest first; in the scenario the stock launcher is enabled before HOME goes back
  to it, and our launcher is removed after (asserted in `RestoreCommandsTest` and observed in both
  script runs). Repeated changes to one target unwind through each prior to the original.
- restore.sh safety: every free-text value (nickname, model) is ASCII-cleaned, capped and only in a
  comment or a single-quoted assignment; TV lines go through `shWord` (double quotes only when no
  `$`, backtick, backslash, `"` or `!`); the TV's own model reaches only a double-quoted assignment
  and `printf %s`. Hostile nickname and model tests pass under `sh -n` and real runs, and the same
  hostile values stayed inert in PowerShell. The identity check runs before any write, reads only
  `getprop`, stops with exit 3 on another TV or with no sha256 tool, and `--allow-other-tv` is the
  only way past. Uninstall runs only with `--remove-apps` (`-RemoveApps`); `commands.txt` comments it.
- Zip reader: allowlisted names only (no zip slip), each once, 8 MiB per entry and 32 MiB in all
  counted on decompressed bytes, every entry hashed against the manifest both ways, the snapshot's
  own contentHash re-checked by `SnapshotCodec.decode`, and grammars re-checked by `ChangeJson`.
- Privacy: `snapshot.json` blanks `serialLast4` and recomputes the hash; no endpoint, subnet, adb
  key id or Wi-Fi field is written anywhere; `restore-point.json` has no nickname.
- Determinism: fixed entry order and timestamp (now zone independent); manifest and JSON key order
  fixed.
- Module graph and dependencies: `:core:backup` adds only `kotlinx-serialization-json` (already in
  `coreCommon` of `ModuleRules.allowedExternal`) and `testImplementation(:testing:fixtures)`;
  `checkModuleGraph` passes. No shared file changed. No frozen signature changed.
- Style: no em dash or double hyphen in prose; no co-author trailers in the author's commits.

## restore.ps1 run evidence

The author had never executed `restore.ps1`. R5 added `RestoreShellTest.writeAPowerShellHarness`,
which writes `core/backup/build/ps-harness/`: `restore.ps1` and `restore.sh` taken from an exported
and re-read zip of the test scenario, `restore-hostile.ps1` from a zip made for a hostile nickname
and model, the stub adb (`src/test/resources/stub/adb`, unchanged), and the fake TV after the plans
(`after/tv`) and at the baseline (`before/tv`). The build fetched it back (`FETCH_BACK`), and a
driver script ran it on forge under the build lock:

```
flock -w 3600 $FORGE_ROOT/.cyt-forge.lock \
  docker run --rm --name cyt-<timestamp>-r5ps --memory 1g --cpus 2 -v <harness>:/h:ro \
  mcr.microsoft.com/powershell:latest sh /h/run-ps.sh
```

script the Kotlin tests use; `pwsh` calls it as `adb` from PATH. Each scenario starts from a fresh
copy of `after/tv`; "state" below is every package state, setting, written file and HOME.
