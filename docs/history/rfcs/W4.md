# RFCs from W4 (probe, profiles, config codec)

## RFC-W4-1 `input_action` and `module_cards` in the launcher config types

Status: accepted (DECISIONS-W1 Rulings, 2026-10-19) and applied at integration (T3):
`LauncherConfigExtras` is gone and the codec models both keys. The text below is the proposal as
filed.

What: add `inputAction: String? = null` and `moduleCards: Boolean? = null` to `LauncherConfigDoc`
(section 5.7), and `inputAction: String` and `moduleCards: Boolean` to `EffectiveConfig`.

Why: upstream main `1bbf0c9` added both keys to `Config.java` (`input_action`, the action an HDMI
or AV row sends where nothing answers `ACTION_VIEW`, XGIMI's `com.xgimi.action.hdmiPlayer`; and
`module_cards`, which turns the card feature off). Section 5.7 predates them. The codec must match
the latest main, so until this lands it carries both keys in `LauncherConfigDoc.unknown` under
their real names, writes them at their `Config.java` position, and reads them with
`LauncherConfigExtras` (`inputAction(doc)`, `moduleCards(doc)`, `effective(doc)`, `withInputAction`,
`withModuleCards`, `builtInDefaults` = `""` and `true`). The differential test checks the extras
against the real latest `Config.java`.

Who is affected: W4 (codec; moves the two keys out of `unknown`), W3 (`ApplyTheme` planning,
none if it only passes docs through), W8 (the Home screen settings, if it ever shows either), W1
(fakes: none take these types). The launcher bundled for 0.1 is built from `7205769`, which ignores
both keys, so nothing changes on the TV until the pin moves.

Smallest alternative: keep the `unknown` carriage and `LauncherConfigExtras` as they are (no
frozen change at all). This is what the W4 branch ships today.
